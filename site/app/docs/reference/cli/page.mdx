# Command line

An app whose `main` hands its arguments to [`cli.Main`](https://pkg.go.dev/github.com/thec1oud/galleon/cli#Main) runs these commands, as `<app> <command>`, where `<app>` is its binary. Without a command, it serves. Each command builds the app as `main` configures it, so it reads the same config file and environment, and its migrators and policy are the ones the app boots with ([0500](/docs/decisions/0500-commands-are-subcommands-of-the-apps-binary)).

```go
func main() {
	os.Exit(cli.Main(context.Background(), os.Args[1:], options()...))
}
```

Reports go to stdout, and errors and usage to stderr. The app's logs go wherever its logger writes them, stderr by default. `<app> help` lists the commands, and `<app> help <command>`, or `-h` after a command, prints its flags and exit codes.

## Exit codes

| Code | Meaning |
|---|---|
| `0` | The command did what it was asked. |
| `1` | The app didn't boot, or the command failed, was refused by the policy, or found a migrator not ready. |
| `2` | The command line is wrong; usage goes to stderr. |

Each command's section says what `0` and `1` mean for it.

## serve

```sh
<app> serve
```

Run the app: start it, serve until SIGINT or SIGTERM, then drain and stop.

This is what the binary does without a command. At boot the app acts on its migrators as the `migrate` config section's `mode` says: `off`, `verify` (the `Production` default) or `apply`.

| Exit code | When |
|---|---|
| `0` | The app stopped cleanly. |
| `1` | The app didn't boot or start, failed while running, or didn't stop cleanly. |

## migrate status

```sh
<app> migrate status
```

Print each migrator's status: its state, whether the policy counts it ready, its drift and its background tasks.

Reads the database and changes nothing. It exits 1 when any migrator isn't ready, so a deploy can check the schema before it sends traffic.

| Exit code | When |
|---|---|
| `0` | Every migrator is ready. |
| `1` | The app didn't boot, a status couldn't be read, or a migrator isn't ready. |

## migrate plan

```sh
<app> migrate plan [-offline]
```

Print what migrate apply would do: each migrator's pending steps, their risks, the plan's fingerprint, and whether the policy would refuse it.

It changes nothing. Approve a plan by pinning its fingerprint in the `migrate` section's `approve` key, or `<APP>_MIGRATE_APPROVE`, as `name=fingerprint` pairs.

With `-offline`, a migrator that can plan without a database plans every change as if the database were empty, and one that can't says so. The providers the migrators need still start, so the database must be reachable even then.

| Flag | Default | What it does |
|---|---|---|
| `-offline` | `false` | Plan without reading the database's state. |

| Exit code | When |
|---|---|
| `0` | Every migrator planned, and the policy allows every plan. |
| `1` | The app didn't boot, a plan couldn't be made, a status couldn't be read, or the policy would refuse a plan. |

## migrate apply

```sh
<app> migrate apply
```

Apply every migrator's pending changes, in order, each under its coordination lock, and stop at the first failure.

The policy still applies: the risk ceiling, unknown risk and approved fingerprints refuse a plan here as they do at boot. The `mode` doesn't: `migrate apply` applies whatever it is.

It waits for the lock as `lock_wait` says, and has no time limit of its own: SIGINT or SIGTERM cancels it. With `coord/local`, whose lock holds within one process, don't run it while a node applies at boot.

| Exit code | When |
|---|---|
| `0` | Every migrator is applied, or had nothing pending. |
| `1` | The app didn't boot, or an apply failed or was refused. |
